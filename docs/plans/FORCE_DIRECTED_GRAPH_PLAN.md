# Force-Directed Graph Plan

## Status

Planned. This plan covers a client-side, force-directed layout for the Atlas
graph. It does not change the SMG schema or the persisted graph.

## Problem

Atlas currently places nodes using a deterministic cluster/time scatter. That
layout is useful for a stable overview, but it does not expose the geometry
implied by the visible relationships. A force-directed layout should make
densely connected groups contract, weakly connected groups separate, and
important bridges remain legible.

## Current constraints and terminology

1. The UI is dependency-free browser JavaScript and renders the graph to a
   `canvas` in `ui/app.js`.
2. `state.edges` contains typed, normalized edges: embedding cosine, spectral
   cosine, history links, and code-topology call/import edges.
3. Projection already applies view mode, history visibility, identity
   projection, filters, thresholds, and the selected topology snapshot.
4. Node coordinates are currently ephemeral and generated by
   `buildGraphLayout()`; no coordinates are stored in SMG JSON.
5. “Force-directed” means a numerical layout simulation, not a new graph
   relationship and not a replacement for spectral clustering.

## Decisions for the first implementation

1. Add a `Force` Atlas mode alongside the existing Field, Neighborhood,
   Bridges, and Matrix modes. Field remains the default.
2. Layout only the current projected node and edge set. Changing filters,
   graph mode, history visibility, or topology snapshot restarts the force
   layout from the current coordinates when possible.
3. Keep coordinates in browser memory only. Reloading a file may use the same
   deterministic seed, but the graph file is not modified.
4. Use a deterministic seeded initial position derived from `note_id`, with
   the current Field layout as the fallback initial arrangement. The same
   graph, projection, and settings must produce the same initial state.
5. Treat edges as undirected visual constraints. Edge weight influences
   attraction only after relation-specific normalization; raw embedding,
   spectral, history, call, and import weights must not be compared directly.
6. Use relation-specific defaults: topology and history are structural
   anchors, spectral and embedding edges are softer semantic constraints.
   The user can enable/disable relation types using the existing edge filter.
7. Run the simulation outside the main rendering path, preferably in a
   Web Worker. The main thread remains responsible for canvas drawing,
   pointer interaction, selection, pan, zoom, and fit-to-view.
8. The simulation stops at a measurable convergence condition or iteration
   cap; it must not continue consuming CPU after convergence.

## Scope

### Included

1. A force-layout mode and controls for restart, pause/resume, and fit.
2. Attraction for visible edges, node repulsion, centering, collision
   padding, and bounded coordinates.
3. Stable node identity and preservation of positions across non-destructive
   filter changes.
4. Typed-edge normalization and relation-aware visual/layout strength.
5. Graceful behavior for empty graphs, singleton graphs, disconnected graphs,
   graphs with no edges, and large graphs.
6. Worker protocol tests or pure-function tests for deterministic layout
   inputs, edge normalization, convergence, and malformed messages.
7. UI documentation describing the mode and the fact that positions are not
   persisted.

### Excluded

1. Persisting coordinates in SMG JSON or adding a layout version to the file
   format.
2. Recomputing embeddings, spectral similarity, clusters, or topology in the
   browser.
3. Changing edge semantics, thresholds, identity resolution, or topology
   snapshot selection.
4. A WebGL renderer, unless performance measurements show canvas plus a worker
   cannot meet the stated limits.
5. Automatic graph editing based on the computed positions.

## Behavioral specification

### BDD scenarios

#### Force mode activation

**Given** a loaded graph and Atlas view  
**When** the user selects `Force`  
**Then** the UI projects the same nodes and typed edges used by the current
   filters, starts or resumes a force simulation, and labels the stage as a
   force-directed layout.

#### Edge-filter change

**Given** a running or converged force layout  
**When** the user changes the active edge type or threshold  
**Then** edges no longer in the projection exert no force, retained node
   positions are reused by `note_id`, new nodes receive deterministic
   positions, and the simulation restarts with bounded alpha.

#### Topology snapshot change

**Given** Force mode and code-topology edges are visible  
**When** the user selects another topology snapshot  
**Then** the layout uses only that snapshot’s projected call/import edges and
   re-equilibrates without changing note identity or persisted data.

#### Convergence

**Given** a finite projected graph  
**When** maximum displacement remains below the convergence epsilon for the
   required consecutive ticks, or the iteration cap is reached  
**Then** the worker reports `converged` and performs no further simulation
   ticks until the projection or layout settings change.

#### Interaction

**Given** a node is being dragged in Force mode  
**When** the pointer moves  
**Then** that node is pinned to the pointer, neighboring nodes respond during
   the bounded reheating period, and releasing the pointer unpins it unless
   the user explicitly pins it.

#### Invalid or empty input

**Given** an empty projection, one node, malformed edge endpoint, NaN weight,
   or a disconnected component  
**When** Force mode is rendered  
**Then** the UI does not throw, invalid edges are ignored, all valid nodes are
   shown, and the stage reports a useful empty/singleton/converged state.

## Algorithm contract

The implementation may use a standard force algorithm, but it must expose a
small pure core with these inputs and outputs:

```text
LayoutInput {
  nodes: [{ id, x?, y?, radius? }],
  edges: [{ source, target, relation, normalized_strength }],
  width, height,
  seed,
  settings
}

LayoutOutput {
  positions: [{ id, x, y, vx, vy }],
  alpha,
  tick,
  status: "running" | "converged" | "capped"
}
```

Required invariants:

1. Every output position corresponds to exactly one input node ID.
2. No output coordinate or velocity is non-finite.
3. Unknown edge endpoints are ignored before force calculation.
4. Self-edges do not create attraction.
5. Symmetric visual edges contribute symmetrically to the force calculation.
6. A fixed seed and identical input produce identical output within the
   JavaScript number model.
7. Coordinates remain within a finite simulation envelope and are mapped to
   the existing pan/zoom transform for display.

Recommended initial settings (to be validated against measurements):

| Setting | Initial value | Contract |
| --- | ---: | --- |
| initial alpha | 1 | Decays after each tick |
| alpha minimum | 0.001 | Simulation stops at or below this value |
| convergence epsilon | 0.25 px/tick | Maximum displacement |
| stable ticks | 8 | Consecutive ticks below epsilon |
| iteration cap | 600 | Hard upper bound per restart |
| node collision padding | 3 px | Prevents visual overlap |
| position update rate | 30–60 Hz | Worker-to-main-thread limit |

These values are implementation defaults, not user-visible guarantees until
the performance pass validates them.

## Relation normalization

Create one pure normalization function that maps each visible edge to a
bounded layout strength and keeps the original display weight unchanged.

1. Embedding and spectral cosine values are clamped to their configured
   visible ranges and normalized relative to the active threshold/range.
2. History links use a fixed structural anchor strength; their multiplicity or
   degree must not accidentally overpower the layout.
3. Call and import edges use separate fixed defaults so a dense import graph
   does not make calls indistinguishable in diagnostics.
4. Duplicate undirected constraints with the same relation are coalesced
   before simulation; the strongest retained constraint wins.
5. The inspector and legend continue to report the source relation and source
   score, never the internal force strength.

## UI and interaction design

1. Add `Force` to the graph-mode control and update the stage eyebrow/title.
2. Add compact controls visible only in Force mode:
   - restart layout;
   - pause/resume;
   - optional “reheat on filter change” behavior, enabled by default.
3. Reuse existing fit, label, selection, drag, pan, and zoom affordances.
4. Show a non-blocking status such as `Layouting`, `Converged`, or
   `Iteration cap reached`; do not imply that coordinates are semantic data.
5. Keep the existing Field mode unchanged, including its deterministic layout.
6. When the graph is too large for the interactive budget, reduce simulation
   detail using a documented policy: cap visible nodes/edges or use a bounded
   approximation, and tell the user what was reduced. Do not silently omit
   nodes.

## Performance and correctness targets

Targets must be measured in a production browser on representative fixtures:

1. For 500 visible nodes and 2,000 visible edges, the first usable positions
   arrive within 250 ms and the main thread remains below 16 ms per render
   frame during simulation.
2. For 2,000 visible nodes and 10,000 visible edges, the UI remains responsive
   to pan, zoom, and selection; worker updates are coalesced to at most 60 per
   second.
3. A layout restart does not allocate unbounded history or retain terminated
   workers.
4. Repeated activation, filter changes, and file reloads leave at most one
   active worker and no stale worker may overwrite the current layout.
5. Deterministic fixture tests verify stable initial positions and valid final
   coordinates.

If the targets cannot be met with the initial algorithm, optimize the worker
and edge projection first. Only then consider Barnes–Hut repulsion or a
rendering change; do not introduce a dependency without a measured need.

## Implementation passes

### Pass 1 — Pure layout core

1. Define the layout input/output and settings.
2. Implement seeded initialization, forces, integration, convergence, caps,
   pinning, and finite-coordinate guards.
3. Add deterministic and degenerate-case tests.

### Pass 2 — Worker transport

1. Add a worker script with versioned `init`, `tick`, `pin`, `release`,
   `pause`, `resume`, and `stop` messages.
2. Add request/session IDs so stale results are discarded.
3. Coalesce position updates and terminate workers on reload/mode changes.
4. Test malformed messages and lifecycle cleanup.

### Pass 3 — UI integration

1. Add Force mode and status/controls.
2. Feed the already-projected graph into the worker.
3. Preserve/reuse positions by note ID and map worker coordinates through the
   existing canvas transform.
4. Integrate drag pinning, selection, fit, labels, and empty states.

### Pass 4 — Performance and usability

1. Add representative JSON fixtures for semantic-only, history-heavy,
   topology-heavy, disconnected, and large graphs.
2. Measure the targets above and tune defaults.
3. Add a bounded large-graph policy only if measurements require it.
4. Update `ui/README.md` and relevant user documentation.

### Pass 5 — Verification and commit

1. Run `node --check ui/app.js` and worker syntax checks.
2. Run the repository Rust format, clippy, and test commands; this feature
   should not alter Rust behavior, but the workspace gate remains mandatory.
3. Manually verify Field/Force parity of projected nodes and edges, snapshot
   switching, drag behavior, reload cleanup, and threshold changes.
4. Commit each implementation pass separately, per repository workflow.

## Open product decisions

1. Should a dragged node remain pinned across filter changes, or only until
   pointer release? Recommended default: release unpins it; explicit pinning
   persists for the current graph session.
2. Should Force mode include all visible relation types by default, or only
   history plus topology? Recommended default: all visible types, with
   relation-specific strengths and the existing filter as the control.
3. Should the layout be reproducible across browsers? Recommended requirement:
   deterministic initialization and test-level reproducibility; exact final
   floating-point coordinates across engines are not a product guarantee.
4. What is the maximum visible node count before reduction? This should be set
   from the performance fixture rather than an arbitrary number.

## Completion criteria

The feature is complete when Force mode is selectable, uses exactly the
current projected graph, is deterministic at initialization, converges or
caps without runaway CPU, supports selection/drag/pan/zoom/fit, handles all
specified degenerate inputs, passes the performance targets or documents a
visible reduction policy, and has no schema or persisted-data changes.
